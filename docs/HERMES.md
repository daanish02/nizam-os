# Hermes — Config Reference

**Last updated:** 2026-07-01

Curated reference for nizam-os-relevant Hermes config. Covers only what is actually used or directly relevant to this project. For full Hermes docs read the official docs locally (`hermes docs` or equivalent).

**Critical constraint:** `~/.hermes/` source code and runtime files are read-only. Configure behaviour only via `hermes/profiles/<name>/` files in this repo. Never modify `~/.hermes/` directly.

---

## Profile structure

```
hermes/profiles/<name>/
├── config.yaml        # all agent config
├── SOUL.md            # personality and tone only — no mandates, no file paths
├── AGENTS.md          # mandate, rules, domain knowledge — auto-injected at session start
├── .env               # DISCORD_TOKEN, DISCORD_GUILD_ID, LITELLM_MASTER_KEY (gitignored)
├── .env.example       # non-secret template — committed. Auto-generated by hermes-profile-watcher on first encrypt.
├── .env.enc           # sops-encrypted .env (committed)
├── skills/            # custom skill files (.md)
└── memories/
    ├── USER.md        # pre-seeded user context — static, version-controlled, never pruned
    └── MEMORY.md      # agent's auto-written memories — grows at runtime, may be pruned
```

Files are symlinked from `hermes/profiles/<name>/` into `~/.hermes/profiles/<name>/` via `scripts/setup/wire-hermes-profile.sh`. Hermes reads from `~/.hermes/`; edits in `hermes/profiles/` propagate via the symlinks.

## config.yaml — key fields

Only fields relevant to nizam-os profiles. Many Hermes defaults are fine and not shown.

### Model

```yaml
model:
  default: deepseek/deepseek-v4-flash
  provider: custom:litellm
  base_url: http://localhost:4000
  api_mode: chat/completions

custom_providers:
- name: litellm
  base_url: http://localhost:4000
  key_env: LITELLM_MASTER_KEY    # reads from profile .env
  api_mode: chat/completions
```

All profiles use `deepseek/deepseek-v4-flash` via LiteLLM proxy. LiteLLM routes to OpenRouter.

### Compression model

```yaml
auxiliary:
  compression:
    provider: custom:litellm
    model: deepseek/deepseek-v3-0324
```

Pin this on every profile. Without it, `provider: auto` uses the primary model — expensive. Compression is how Hermes summarises long sessions to fit context. `deepseek-v3-0324` costs near zero.

### Security

```yaml
security:
  allow_lazy_installs: false   # agents cannot run pip install at runtime
  redact_secrets: true         # scrubs secrets from tool output

approvals:
  mode: manual                 # all tool calls require approval (default)
  cron_mode: deny              # cron jobs blocked unless explicitly allowed
```

`allow_lazy_installs: false` is mandatory. Default is `true`. Without this, agents can silently install packages.

### Toolsets

Available toolsets for `discord` platform. List only what the agent actually needs.

```yaml
platform_toolsets:
  discord:
    - memory          # persistent memory across sessions
    - skills          # load custom .md skill files
    - clarify         # ask user a question before proceeding
    - delegation      # spawn child agents (Reem only — sandbox dev agents)
    - kanban          # task board (Raha only — NOT in the default discord wildcard)
    - terminal        # shell access (Nazim, Reem — scoped by command_allowlist)
    - file            # read/write files on VPS (Nazim, Reem)
    - web             # web search + URL extraction (Omar, Reem, Mira)
    - image_gen       # image generation (Mira — if backend available)
    - cronjob         # create scheduled jobs (Nazim, Raha)
```

To disable everything not listed: add unwanted toolsets to `agent.disabled_toolsets`. The curator config example shows this pattern.

**`kanban` note:** Not included in the Hermes `discord` platform wildcard. Must be listed explicitly in `platform_toolsets.discord`. Only Raha uses it.

### command_allowlist (terminal toolset)

```yaml
command_allowlist:
  - git log
  - git diff
  - systemctl is-active
  # add only commands the agent's mandate explicitly requires
```

Commands not in this list require manual Discord approval before execution. Keep lists minimal — each entry expands agent autonomy. Per-agent allowlists are in `docs/AGENTS.md`.

### MCP servers — HTTP transport (post Curator v1)

```yaml
mcp_servers:
  knowledge:
    url: http://127.0.0.1:8100/mcp
    tools:
      include:
        - search_vault
        - get_note
        - list_notes
      # prompts: false  (optional — suppress MCP prompt resources)
      # resources: false
```

Use `tools.include` to whitelist specific tools per agent. Omit `include` to expose all tools. Omit `tools` block entirely for full access with no filter.

### MCP servers — stdio transport (current knowledge-service)

```yaml
mcp_servers:
  knowledge:
    command: /home/vazir/.local/bin/uv
    args:
      - run
      - --directory
      - /home/vazir/nizam-os/services/knowledge-service
      - --env-file
      - /home/vazir/nizam-os/secrets/nizam.env
      - python
      - server.py
    tools:
      prompts: false
      resources: false
```

Hermes spawns one process per session, kills on session end. Replaced by HTTP transport in Curator v1.

### MCP servers — npx (GitHub, Reem only)

```yaml
mcp_servers:
  github:
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: ${GITHUB_PAT}
    tools:
      include:
        - list_issues
        - get_issue
        - list_pull_requests
        - get_pull_request
        - create_pull_request_review
        - list_commits
        - get_commit
```

Requires Node.js on VPS. Check: `node --version`. Install via nvm or apt if missing.

### Discord

```yaml
discord:
  allowed_channels: "<channel_id_1>,<channel_id_2>"   # comma-separated snowflake IDs
  require_mention: true                                 # default — agent only responds when @mentioned
  free_response_channels:                              # channels where no @mention needed
    - <channel_id>
  allow_any_attachment: true                           # accept Discord CDN file attachments
  max_attachment_bytes: 33554432                       # 32MB — default, make explicit
  channel_prompts:                                     # ephemeral per-channel system context
    "<channel_id>": "User is in #finances. Focus on financial queries."
```

Channel IDs are Discord snowflake integers. See `docs/DISCORD.md` → Getting channel IDs.

### Delegation (Reem only — sandbox agents)

Reem uses `delegation` to spawn short-lived sandbox agents for risky dev work. Raha does NOT use delegation — C-suite coordination is via the `kanban` toolset.

```yaml
delegation:
  max_spawn_depth: 1        # Reem → sandbox agent OK. Sandbox agent → anyone: blocked.
  max_concurrent_children: 2
  subagent_auto_approve: false   # sandbox agent tool calls still require approval
```

Sandbox agents never respond to Discord directly. Reem synthesises their output and posts in `#cto-office`.

### Cron

```yaml
approvals:
  cron_mode: deny    # block cron creation (most profiles)
  # or
  cron_mode: manual  # allow cron, but each run requires approval (Raha, Nazim, Noor)
```

Pin the model at cron creation time: `hermes cron create --model deepseek/deepseek-v4-flash "..."`. Without pinning, a model change silently affects all cron behaviour.

### Agent limits

```yaml
agent:
  max_turns: 150           # max tool/response turns per session
  gateway_timeout: 1800    # 30 min — session timeout
```

## SOUL.md rules

**Personality and tone only.** Hermes injects SOUL.md as the system prompt prefix.

Include:
- Name and role description
- Communication style (terse, proactive, formal, etc.)
- Formatting rules (no emojis, Discord code blocks, etc.)
- What the agent does NOT do (no workarounds, no improvising taxonomy, etc.)

Do NOT include:
- File paths
- Tool names or usage instructions
- Workflow rules or mandates
- Anything that belongs in AGENTS.md

Rationale: SOUL.md sets character. AGENTS.md sets mandate. Mixing them adds prompt weight and makes the agent harder to update.

---

## AGENTS.md rules

**Mandate, rules, domain knowledge.** Auto-injected as project context at session start (same mechanism as CLAUDE.md in Claude Code).

Include:
- Domain vocabulary and definitions
- Workflow rules (approval gates, logging policy, escalation)
- Data access rules ("never write outside commons/")
- Failure rules ("if X fails, stop — do not workaround")
- Channel context if needed

Do NOT include:
- Personality or tone (belongs in SOUL.md)
- Implementation commands (belongs in plans)
- Full tool documentation (Hermes auto-discovers via `list_tools()` — repeating it wastes tokens)

## Skills

Custom skills live in `hermes/profiles/<name>/skills/` or `hermes/skills/` (shared). Format: `.md` files following the [agentskills.io open standard](https://agentskills.io).

Skills are loaded at session start when referenced in `config.yaml` or triggered by name. The `skills` toolset must be enabled for the profile.

Skills that are never loaded on any nizam-os profile: Apple, macOS, iOS, Xcode, Homebrew (system is Linux/VPS only).

## Memory

Hermes memory is per-profile, persisted across sessions, stored in `hermes/profiles/<name>/memories/`. Symlinked into `~/.hermes/profiles/<name>/memories/` via `wire-hermes-profile.sh`.

Agents write memories automatically when `memory` toolset is enabled and `memory.write_approval: false`. To require approval for memory writes: set `memory.write_approval: true`.

---

## USER.md rules

**Pre-seeded user context.** Lives in `memories/USER.md`. Static, version-controlled, never pruned by the memory curator.

Include:
- User's name and key relationships
- Preferences the agent should always know (language, currency, timezone)
- Recurring facts about the user's situation (accounts, categories, vault structure)
- Context that would otherwise take many sessions to re-establish

Do NOT include:
- Agent personality or mandate (belongs in SOUL.md and AGENTS.md)
- Workflow rules (belongs in AGENTS.md)
- Anything the agent should discover dynamically (tool outputs, current task state)

Rationale: USER.md is the agent's permanent mental model of the user. It seeds the memory system with facts that are always true, so the agent doesn't re-learn them each session.

---

## MEMORY.md rules

**Auto-written agent memories.** Lives in `memories/MEMORY.md`. Grows at runtime. May be pruned or consolidated by Hermes' memory curator when it grows large.

Contains what the agent has learned across sessions: past decisions, user corrections, observed patterns, things the user said to remember.

Do NOT manually edit MEMORY.md in normal operation — it is the agent's running state. Pre-seed constants in USER.md instead. If memories become stale or wrong, instruct the agent to update or remove them via the `memory` toolset.

## Hermes profile watcher

`hermes-profile-watcher.service` (user service) — bidirectional sync between `hermes/profiles/` and `~/.hermes/profiles/`. Monitors with inotifywait. On profile file change: re-links + auto-encrypts `.env` via `scripts/encrypt-profile-env.sh`.

Start once after install: `systemctl --user enable --now hermes-profile-watcher`.
