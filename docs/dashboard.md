# Dashboard guide — nizam-os

Three dashboards. Each covers a distinct concern.

| Dashboard | UID | What it covers |
|---|---|---|
| Nizam — Agents | `nizam-agents` | LLM cost, tokens, cache, latency, tool usage |
| Nizam — Services | `nizam-services` | Service UP/DOWN, gateway health, infra status |
| Nizam — System | `nizam-system` | CPU, RAM, disk, network, processes, security |

---

## Nizam — Agents

Variables at the top: **Model** and **Agent** — filter all panels. Default: all.

### Row 1 — Today snapshot (6 stat tiles)

| Tile | Metric | Notes |
|---|---|---|
| Calls Today | `nizam_llm_requests_today` | LLM requests since midnight UTC. Resets daily. |
| Tokens In Today | `nizam_llm_input_tokens_today` | Prompt tokens sent. High = expensive context or many calls. |
| Tokens Out Today | `nizam_llm_output_tokens_today` | Completion tokens received. |
| Spend Today | `nizam_llm_spend_usd_today` | USD spent today. Orange at $2, red at $5. |
| Cache Hit Rate | `nizam_llm_cache_hit_rate_today * 100` | % of calls with a cache hit. Green ≥ 40%, red < 20%. |
| Cache Savings Today | `nizam_llm_cache_savings_usd_today` | USD saved via provider prompt cache today. $0 when no cache reads. |

### Row 2 — This Month

| Tile | Metric | Notes |
|---|---|---|
| Spend This Month | `nizam_llm_spend_usd_this_month` | Calendar-month total. Orange at $60, red at $90. |

### Row 3 — Rates (timeseries, last 10m window)

| Panel | What to watch |
|---|---|
| Cost Rate — by Model | Spend per hour per model. Spike on one model = specific agent active. All spike = delegation fan-out or cron. |
| Token Rate — In / Out / Cache Read | Tokens per minute. Cache Read climbing = good. Output > Input = verbose responses. |

### Row 4 — Efficiency (timeseries)

| Panel | What to watch |
|---|---|
| Cache Tokens — Creation vs Read | Creation = writing to provider cache (billed at premium). Read = serving from it (discounted). Read > Creation = cache is working. |
| Avg Response Latency — by Model (1h rolling) | End-to-end ms per model. All models spiking = VPS pressure — cross-reference System dashboard. |

### Row 5 — Tool Usage (bargauges, today / all-time)

Generated by `scripts/metrics-toolcalls.py` every 5 min, reading `agent.log` files across all profiles.

| Panel | Metric | Notes |
|---|---|---|
| Tool Calls Today — by Tool | `nizam_tool_calls_today` | How many times each tool fired today. Sorted descending. |
| Tool Error Rate | `nizam_tool_errors_total / nizam_tool_calls_total * 100` | % of calls that errored. Green < 25%, red > 75%. |
| Tool Duration — Cumulative Wall Time | `nizam_tool_duration_seconds_total` | Total seconds spent in each tool across all retained logs. |
| Tool Output Size Today | `nizam_tool_output_chars_today` | Chars returned by each tool today. High chars = that tool's output is inflating input tokens on next call. |
| Tool Output Size — All Time | `nizam_tool_output_chars_total` | Cumulative output chars across all retained log files. Use this to identify structurally heavy tools. |

Output size is the most actionable metric here: a tool that returns 50k chars per call costs far more than one returning 100 chars, because that output lands in the next request's context.

### Row 6 — All-time spend breakdowns (bargauges + pie)

| Panel | What it shows |
|---|---|
| Spend by Model | Cumulative USD per model. Longest bar = most expensive model overall. |
| Spend by Provider | Pie split by provider. |
| Spend by Agent | Cumulative USD per Hermes profile. Identifies cost-heaviest agent. |

### Row 7 — All-time totals (stat tiles)

Total Calls · Total Tokens In · Total Tokens Out · Total Spend — cumulative since DB was first populated. Do not reset on Prometheus restart.

### Row 8 — All-time cache

| Tile | What it shows |
|---|---|
| Cache Savings (All Time) | Total estimated USD saved via provider prompt cache. |
| Cache Read Tokens (All Time) | Total tokens served from cache. High = stable system prompts, cache working as intended. |

### Row 9 — Activity Heatmap

Token throughput (input + output tokens/min) over time. Darker = more active. Useful for spotting usage patterns across the day/week.

## Nizam — Services

Refreshes every 30s. Default time range: last 24h.

### Top stat tiles

| Tile | Metric | Notes |
|---|---|---|
| Services Up | `nizam_services_up_total / nizam_services_total * 100` | % of tracked services active. Red < 80%, orange < 95%, green ≥ 95%. |
| Down | `nizam_services_total - nizam_services_up_total` | Raw count of services currently down. Green = 0, orange ≥ 1, red ≥ 3. |
| LiteLLM Proxy | `nizam_llm_proxy_up` | Proxy reachable from the metrics script. DOWN = no agents can make LLM calls. |

### Service Status — 24h History (state timeline)

One row per tracked service. Red = DOWN, green = UP. Shows transitions over the last 24h so you can see exactly when something went down and recovered.

### Current Status (table)

All services sorted by status ascending — DOWN rows appear first. Columns: Service · Type · Status (red/green cell). `Type` is `system` (root systemd) or `user` (hermes gateway, vazir user unit).

When a service shows DOWN:
```bash
sudo systemctl status <service>       # system units
systemctl --user status <service>     # user units (hermes gateways)
```

### Data source

`scripts/metrics-services.sh` reads `inventory/tracked-services.txt`, calls `systemctl is-active` for each entry, writes `nizam-services.prom` every 5 min via `metrics-services.timer`. Up to 5 min stale.

To add a service to tracking: add it to `inventory/tracked-services.txt` (not `services.txt` — that file is auto-generated).

## Nizam — System

Covers host-level health. Do not duplicate these in other dashboards.

| Section | What it shows |
|---|---|
| Top row | Uptime, CPU %, RAM %, Disk %, Load avg (1m), TCP connections |
| CPU / Memory | Timeseries. RAM tracks used, cached, available. |
| Network I/O / Disk I/O | Timeseries per interface / device. |
| Load Average / Disk usage by directory | Load 1/5/15m · Per-directory disk usage bar. |
| Top CPU / Memory Processes | Bargauge ranked by current consumption. |
| Security | SSH failed logins, invalid users, banned IPs, UFW blocked packets — from fail2ban + auth.log. |
| Security Events | Timeseries of login failures and bans over time. |
