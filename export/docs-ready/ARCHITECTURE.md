# Architecture

This document describes how the system is built. It implements the design in
`export/00-START-HERE.md` and the requirements in `SRS.md`. It absorbs the prior
iteration's SERVICES.md and INTEGRATIONS.md, because doc sprawl was a real
problem last time (`export/BUGS-AND-GOTCHAS.md` #8). It is the single
reference for components, ports, units and data flow. Security controls live
in `SECURITY.md`; interface contracts live in `docs/specs/`.

## Components

| Component | What it is | Where | Reaches |
| :--- | :--- | :--- | :--- |
| Discord | The only surface. Three bot applications: Nazim, Noor, Ayah. | External | Hermes gateways |
| Hermes gateways | One systemd **user** unit per agent profile (`hermes-gateway-{admin,curator,assistant}`), generated by Hermes's own gateway installer. Each runs the LLM agent loop, holds memory, calls MCP tools. | user scope, as `vazir` | `nizam-mcp`, LiteLLM |
| `nizam-approval` Hermes plugin | A `pre_tool_call` hook that sends every approved write to the owner's Discord `/approve` gate. See `SECURITY.md` and spec 004 "Enforcement mechanism". | loaded by each gateway | — |
| `nizam-mcp` | The single daemon: one Python process (`python -m nizam serve`) serving every domain's MCP tools over streamable HTTP. System unit, running as `User=vazir`. | `127.0.0.1:8100` | Postgres, LiteLLM, vault, public web, FX/metal-price API |

## Ownership split with `nizam-dotfiles`

| Concern | Owner |
| :--- | :--- |
| SSH hardening, UFW, fail2ban, unattended-upgrades, Tailscale | `nizam-dotfiles` |
| Prometheus, node-exporter, Grafana, Loki, Promtail install + host metrics (`metrics-*` units) | `nizam-dotfiles` |
| Postgres, pgvector, Redis, uv, age/sops, dbmate, LiteLLM, Hermes | `nizam-os` (`scripts/bootstrap.sh`) |
| Nizam units, dashboards, app metrics, Promtail job for Nizam logs | `nizam-os` (`deploy/`) |

**Unit naming rule.** Every systemd unit nizam-os installs is either
`litellm-proxy.service` or `nizam-*`. `nizam-dotfiles` already owns names like
`metrics-services.*`, and the old system collided on exactly that name. Cycle-1
nizam-os units:

| Unit | Scope | Purpose |
| :--- | :--- | :--- |
| `litellm-proxy.service` | system | LLM proxy |
| `nizam-mcp.service` | system | the MCP daemon |
| `nizam-retry-embeddings.{service,timer}` | system | every 10 minutes, backfill `embedding_status='pending'` (ADR-006) |
| `nizam-backup.{service,timer}` | system | nightly at 03:30: `pg_dump`, Hermes memories/skills tarball, vault commit+push |
| *(no unit)* `python -m nizam jobs reindex` | manual | rebuild the knowledge index from vault files (spec 001 K-2) — recovery tool, run by hand |
| `nizam-metrics-*.{service,timer}` | system | app textfile metrics (LLM spend, tool calls, service health) |
| `hermes-gateway-{admin,curator,assistant}.service` | user | generated by Hermes, not by `deploy/manifest.txt` |

## The `nizam-mcp` daemon

One process and one package (`nizam`) — ADR-001. It mounts one streamable-HTTP
MCP endpoint per domain:

- `/knowledge/mcp` — spec 001
- `/finance/mcp` — spec 002
- `/calc/mcp` — spec 003. Pure, read-class tools. The same functions are also
  imported in-process by `nizam/finance/`.
- `/health` — plain HTTP, no auth, returns `{status, version, checks: {db}}`
  with a 2s timeout.

**Authentication and scoping.**

- Every MCP request carries `Authorization: Bearer <token>`.
- `nizam/core/auth.py` maps each token to an agent name, and each agent name to
  its allowed domains. A token missing or unknown → 401. A known token outside
  its scope → 403.
- The resolved agent name is the `actor` on every audit row.
- Tokens are read from `MCP_TOKENS` in `~/.config/nizam/nizam-mcp.env`. Each
  agent's own token also sits in its Hermes profile `.env` as
  `NIZAM_MCP_TOKEN`.

**Write tools.** Every write tool is two-pass, and uses `nizam/core/approval.py`
for signed draft tokens (spec 004 "Enforcement mechanism").

**Config.** `nizam/config.py` reads everything once at import. A missing
required value fails startup.

| Variable | Required | Meaning |
| :--- | :--- | :--- |
| `LITELLM_BASE_URL` | no (default `http://127.0.0.1:4000`) | proxy address |
| `LITELLM_API_KEY` | yes | **`nizam-mcp`'s own virtual key**, never the master key |
| `EMBED_MODEL`, `EMBED_DIMS` | yes | embedding model name and vector width |
| `KNOWLEDGE_DSN` | yes | `svc_knowledge` connection string |
| `FINANCE_DSN` | from Phase 7 | `svc_finance` connection string |
| `VAULT_ROOT` | yes | e.g. `/home/vazir/nizam-vault` |
| `MCP_HOST`, `MCP_PORT` | no (default `127.0.0.1`, `8100`) | bind address |
| `MCP_TOKENS` | yes | agent → token map |
| `NIZAM_APPROVAL_KEY` | yes | HMAC key for draft tokens |
| `FETCH_MAX_BYTES`, `FETCH_TIMEOUT_S`, `FETCH_MAX_REDIRECTS` | no (defaults 10 MB / 15 / 5) | Q-K3 |
| `FX_API_URL`, `METAL_PRICE_API_URL` | from Phase 7 | provider chosen at implementation time (spec 002 Q-F3) |

## Agent roster (cycle 1)

| Agent | Hermes profile | `nizam-mcp` domains | Discord channels |
| :--- | :--- | :--- | :--- |
| Nazim | `admin` | **none** — operational only (see below) | `#admin`, `#alerts`, `#logs` |
| Noor | `curator` | `knowledge` | `#knowledge` |
| Ayah | `assistant` | `finance`, `calc` | `#finance` |

Ayah does **not** get knowledge access, not even read-only (owner decision,
2026-09-26). Scoping stays domain-level.

**Nazim** has no `nizam-mcp` scope at all and never touches Postgres. Its tools
are:

- Hermes's terminal tool, restricted by `command_allowlist` to status checks and
  single restarts of `litellm-proxy`, `nizam-mcp`, `hermes-gateway-curator` and
  `hermes-gateway-assistant`, as defined in `SECURITY.md`.
- Read-only file access to this doc set, so it can explain the system.

## Data flow: a knowledge capture

1. The owner posts a link in `#knowledge`.
2. Noor calls `ingest_url(url)` on `/knowledge/mcp`. This is a read-class
   call: `sources/web.py` fetches (C-16, C-17) and extracts, and the tool
   returns an `ExtractedSource`. **Nothing is persisted.**
3. **Noor classifies** the content in her own reasoning: title, areas, tags,
   confidence (FR.03.2.1 — the owner is never asked). She calls
   `add_note(..., approved=false)`. The service validates and returns the draft
   plus a `draft_token`, and still persists nothing.
4. Noor shows the draft. She then calls `add_note(..., approved=true,
   draft_token)` with the identical payload. The `nizam-approval` plugin holds
   the call and raises `/approve` in Discord.
5. The owner approves. `nizam-mcp`:
   - verifies the token
   - writes the Markdown file (file first — it is authoritative)
   - then, in one transaction: the index row, the embedding (or
     `embedding_status='pending'` if the embedding call fails), and the audit
     row with `actor=curator` and the `approval_id`

   If the transaction fails, the file is deleted and the failure is reported
   (spec 001 K-3).
6. If the embedding is pending, `nizam-retry-embeddings.timer` backfills it
   later.

## Data flow: a finance transaction

1. The owner tells Ayah "spent 45 AED on groceries".
2. Ayah calls `record_transaction(..., approved=false)`. The service resolves
   the category (FR.01.1.2) and computes the sub-unit amount via `nizam/calc/`.
   It returns the interpretation plus a `draft_token`.
3. The approved call is held by the plugin until the owner answers `/approve`.
   Then the transaction row and audit row are written in one transaction.
4. Balances are never stored. `report_position` always sums the ledger
   (ADR-005) and converts to AED, stating the rate and its as-of time.

## Deploy model

The release-directory pattern (ADR-002). `scripts/deploy.sh` is written in
Phase 3 — before the first live unit exists — and extended in later phases:

1. `git archive <ref>` into `~/.local/share/nizam/releases/<sha>/`.
2. `uv sync --frozen --no-dev` in that release directory.
3. Atomic flip of `~/.local/share/nizam/current` to the new release.
4. Apply `deploy/manifest.txt`:
   - system unit symlinks into `/etc/systemd/system`
   - Hermes profile links: `config.yaml`, `SOUL.md`, `AGENTS.md`, and the
     `nizam-approval` plugin, into `~/.hermes/profiles/<name>/`
   - the profile `.env` link, from `~/.config/nizam/hermes-<name>.env`
   - root-owned copies: sudoers (checked with `visudo -cf` first), logrotate,
     the Promtail job
5. `daemon-reload` for both system and user scope, then restart only units
   whose content changed. Keep the last 5 releases.

Other modes:

- `--dry-run` prints actions only.
- `--rollback` flips back to the previous release.
- `--sync-secrets` decrypts `secrets/*.env.enc` into `~/.config/nizam/`.

**Nothing live is ever edited directly.**

## Why one daemon, not one per domain

A 2 vCPU / 7.8 GB box doesn't need a process per domain. One process gives one
place for auth, approval, audit and health logic. Isolation between domains is
enforced where it matters for this threat model: DB role grants (C-07) and
token scopes (C-02). See ADR-001.
