# Repository Root Layout

## On `main`

```text
frontend/                  # only if the project has one — see nextjs/project-layout.md
backend/                   # single backend service — OR:
services/                  #   ...multiple: services/<role>/, per python|go/project-layout.md
docs/
├── PRD.md
├── ARCHITECTURE.md
├── diagrams/
├── specs/
│   ├── 001-<concern>.md   # one file per domain concern, numbered for reading order
│   └── 002-<concern>.md   # e.g. 001-auth-api.md, 002-users-schema.md
└── (SCHEMAS.md/APIS.md/... — whichever high-level docs were selected)
scripts/
├── start.sh               # starts all services in one command — generated by write-dev-scripts.sh
├── stop.sh                # stops all services started by start.sh
└── (deploy.sh, migrate.sh, seed.sh — project-specific ops scripts added as needed)
                            # NOT skills/feanor/scripts/, which is Feanor's own tooling and is gitignored
.run/                      # runtime artefacts written by start.sh: *.pid + *.log — gitignored
.github/
├── workflows/             # CI — runs the same checks .pre-commit-config.yaml runs locally
├── dependabot.yml
├── ISSUE_TEMPLATE/
└── PULL_REQUEST_TEMPLATE.md
.pre-commit-config.yaml    # repo root — the pre-commit tool reads this path by default, not configurable
                            # to live elsewhere without extra flags; see git/pre-commit-hooks.md
.gitignore
.env.example                # repo-wide reference documenting every var across every service —
                            # not itself loaded by anything, see "Env Vars" below
README.md
```

Each service under `backend/`/`services/<role>/` and `frontend/` is internally structured per its own language's `project-layout.md` — this file only covers what sits _around_ them at the root.

## Env Vars — Per-Service, Not Shared

Each service/frontend has its **own** `.env` (`backend/.env`, `services/api/.env`, `frontend/.env.local`) — never a single root `.env` loaded by everything. Reasons, not just preference:

- **Docker build context**: a Dockerfile builds from its own service directory; a root `.env` would need to be pulled in from outside that context, which either widens the build context unnecessarily or requires awkward path gymnastics.
- **Blast radius**: a service should only ever have access to the env vars it actually needs. A shared root `.env` means every service can read every other service's variables, which is unnecessary exposure — the same least-privilege reasoning `python/security.md`/`go/security.md`/`nextjs/security.md` already apply elsewhere.
- **Independent deployability**: a service's `.env` living inside its own directory means it doesn't depend on anything existing outside that directory to run.

Root `.env.example` is documentation only — it lists every var across every service (grouped by which service/frontend uses it) so a new contributor can see the whole picture in one place, but nothing actually loads it. Each service's own `.env.example` (per that service's `project-layout.md`) is the one that gets copied to a real `.env`.

## `.github/` vs. `.pre-commit-config.yaml`

These are two different tools with two different, non-negotiable file locations:

- **`.pre-commit-config.yaml`** — the `pre-commit` tool looks for this at the repo root by default. Putting it anywhere else requires passing `--config` everywhere the tool is invoked (locally and in CI), which is extra indirection for no benefit — leave it at root.
- **`.github/`** — GitHub-specific configuration: CI workflows (which should run the _same_ checks `.pre-commit-config.yaml` defines locally, so a skipped local hook doesn't silently pass — see `git/pre-commit-hooks.md`), `dependabot.yml` (per `git/dependabot.md`), issue/PR templates, `CODEOWNERS`.

## `.run/` — Gitignore This

`.run/` holds PID files and logs written by `scripts/start.sh` — add `.run/` to `.gitignore`. Runtime scratch, not project state.

## Feanor's Own Paths: `skills/` and `.feanor/`

`skills/` holds the tool itself (`skills/feanor/`) and is **gitignored** — it is never tracked, on any branch, so it cannot reach `main` and needs no stripping step. The layout above deliberately does not list it.

`docs/plan.toml` is the ticket plan — what was built, in what order, and verified how. It lives in `docs/` with the rest of the project's record rather than under `.feanor/`, because it is a project artifact that outlives the tool: a reader a year later needs it as much as they need the SRS, and a project that gitignores `.feanor/` wholesale would otherwise lose it.

`.feanor/` (`audit_report.md`, `state/`, `logs/`, `profile.toml`) is genuinely tool-internal and tracked on every branch, with only `.feanor/scratchpad/` ignored. See `git/branch-strategy.md`.
